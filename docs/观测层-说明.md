# 观测视图（0.3.0）

## 为什么做

用户想把「记忆底座」和「大脑/上下文」整合。评估后选了 `dsh-context` 作为观测层，
但它没有对外扩展点（host 只注册 `sessionProjections`，不暴露 service / RPC），
无法把记忆卡片直接嵌进它的 Context 面板——那样只能 fork 530KB 客户端，升级维护成本高。

于是改成：记忆侧自己出一个「观测」视图，和 dsh-context 的 Context 标签**并排对照**。

## 做了什么

1. host 端新增 RPC 端点 `observe`（`lib/index.js`）
   - 近 24h 注入次数、平均指针数
   - 近 24h 检索次数、有结果次数（命中率）
   - 库健康：记录数、待审、审计链
2. 客户端新增「观测」标签（`lib/client.js`）
   - 6 个 KPI 卡片 + 一段「怎么读这组数」说明
3. 版本 0.3.0

## 数据来源

- `traces` 表：`op='inject'` 的 `injected` JSON 数组长度 → 指针数
- `traces` 表：`op='search'` 的 `hits` JSON 数组是否非空 → 是否有结果
- `store.stats()`：记录 / 待审 / 审计

## 验证

- `p7` 冒烟（临时库副本）：`injectCount=5, avgPointers=2, searchCount=2, hits=2, records=25, pending=0, auditOk=true`
- `validate-tools`：23 工具
- `p6` 17 项、`p2` 13 项全过

## 局限

- 这是「并排观测」，不是「嵌入 dsh-context 面板」
- 真要嵌入，需要 fork dsh-context 或等它开放 slot / service
- 暂不做「上下文 token 构成」：那部分数据在 dsh-context 的 projection 里，属于它的私有实现
