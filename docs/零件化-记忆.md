# 零件化记忆：把「一切皆零件」落到记忆底座

> 理念来源：B 站《DSH:一切皆零件》（马上淋雨，2026-10-26）。
> 核心：DSH 不该是一个大黑盒，而是**一堆有名字、有契约、可替换的小零件**，按需拼装。

## 原来的问题

记忆底座之前是「一个插件 = 一堆能力」：工具、注入、面板、服务都长在一起。
能力是真的，但**没法被别的插件按需取用**——你只能整体装，不能只要「教训」这一块。

## 零件化之后

### 零件契约

每个零件都是：

```js
{ name, version, describe(), run(store, ctx) -> string[] }
```

- `name`：可被引用的名字
- `version`：契约版本，改行为就升版本
- `describe()`：一句话说明，给人和模型看
- `run()`：纯读取，返回若干行文本

### 当前零件清单（5 个）

| 零件 | 作用 |
|---|---|
| `profile` | 身份与长期事实（高重要性 L1/L2） |
| `recent` | 最近写入 |
| `lessons` | 教训（负面/紧急且高唤醒） |
| `scene` | 指定场景（tag 或 `scene:<名>`） |
| `associations` | 与种子相关的联想（语义/标签/情绪） |

### 装配协议

```js
compose(store, { scene, parts, seed, maxChars })
```

- 按给定顺序跑零件
- **去重**（同一条记忆不会出现两次）
- **限长**（先到先得，超预算就停）
- **带来源标注**（`### profile（v1）`）
- 未知零件不报错，标注「未知零件，已跳过」

### 对外暴露

- 工具：`mem_parts()` 列零件、`mem_compose({...})` 装配
- 服务：`ctx.memory.parts()` / `ctx.memory.compose({...})`

## 为什么这比“一个大工具”好

| 维度 | 大黑盒 | 零件化 |
|---|---|---|
| 复用 | 只能整体用 | 别的插件可只取 `lessons` |
| 演进 | 改行为可能影响所有人 | 零件独立升版本 |
| 可解释 | 出问题难定位 | 每个零件单独可测（p15） |
| 成本 | 一次给一大段 | 按场景和预算装配 |

## 和「服务化」的关系

- 服务化解决「**谁能调**」（进程外 → HTTP API / 进程内 → ctx.memory）
- 零件化解决「**调什么**」（不是“给我记忆”，而是“给我 profile + lessons”）

两者叠起来，别的插件/外部程序可以精确说：**我要这个场景的这两个零件，预算 800 字**。

## 下一步（同一理念的延伸）

- 把**存储层**做成零件（SQLite / 未来图库可替换）
- 把**检索引擎**做成零件（FTS5 / 向量可替换）
- 把**情绪标注**做成零件（规则 / 模型可替换）
- 零件目录对外发布，让别的插件能“逛零件架”

一句话：**记忆不是仓库，是零件架。**
