# 加密（crypto）设计与现状

状态：**已实现（1.7.0，默认关闭）**。

## 为什么不在这一轮直接做

1. **会动存量数据**：加密意味着把 `records.content` 改写成密文，需要一次全库迁移；迁移失败或密钥丢失等于数据报废。
2. **密钥管理是独立设计题**：密钥放哪（DPAPI / 环境变量 / 文件 ACL）、怎么轮换、多设备怎么同步，都要先定。
3. **S 级隔离已有一半保障**：S 级记录本来就不进注入、不进检索、不对外 API、不进情绪事件；加密解决的是“磁盘被拿走”这一层。

所以先把图查询做完，加密留到单独一期，避免在同一轮里同时改数据和改检索。

## 建议方案（下一期）

- 算法：AES-256-GCM，每条记录独立 nonce
- 密钥：`meta/enc.key`（32 字节随机，ACL 仅当前用户；可选 DPAPI 包裹）
- 范围：只加密 `records.content` 与 `affect_events.excerpt`；摘要/标签保持明文（检索依赖）
- 读取：`store.read()` 透明解密；解密失败返回 `{ denied: true, reason: 'key-missing' }`，不抛错
- 迁移：先 VACUUM INTO 备份 → 逐条加密 → 校验可读 → 再删明文列（或保留双写一版）
- 开关：`config.crypto.enabled=false` 默认关；开启前强制备份

## 当前的替代保障

- S 级不进注入/检索/联想/API/情绪事件
- 审计链可检测文件被改
- 数据目录在本地，不联网

## 完成标准（下一期）

1. 开启后重启，所有记录可正常读
2. 关掉密钥后读取返回明确错误，不崩
3. 迁移前后哈希链一致
4. 测试覆盖：加密/解密/密钥缺失/轮换

## 落地记录（1.7.0）

- 文件：`lib/memory/crypto.js`（AES-256-GCM，格式 `enc:v1:<iv>:<tag>:<ct>`）
- 密钥：`dataDir/meta/enc.key`（32 字节 hex，0600 权限，首次 enable 生成）
- 存储：只加密 `records.content`；摘要/标签保持明文
- 读取：`store.read` 自动解密；无密钥/密钥不对返回 `{ denied: true, reason }`，不崩
- 工具：`mem_crypto({ action: status|enable|encrypt|decrypt, record_id? })`
- 测试：p23 9 项（默认关、生成密钥、加解密往返、透明读、坏密钥被拒）
- 注意：`decryptRecord` 后是明文落库；想全库加密需逐条 encrypt（本期不做自动迁移）
