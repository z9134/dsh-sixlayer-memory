# 方案：DSH 工作台 · 一个大插件，两条线

> 一期方案（设计定稿，待批准后开工）
> 日期：2026-11-01

---

## 0. 一句话

把现在的 `dsh-memory-core` 升级成**一个工作台大插件**：
一个安装入口、一个数据目录、一个设置面板，内部拆成**记忆**与**零件**两条线；
记忆是核心（让 AI 记得你、接着干），零件是骨架（让能力可拼、可换、可长）；
对外统一通过 **QQ 机器人** 随时随地使用。

---

## 1. 为什么这么设计

你的诉求是三层：

1. **它能跟我工作** —— 不是问答，是接活、干活、交付
2. **它记得住** —— 记得你是谁、目标是什么、上次做到哪、踩过什么坑
3. **随时随地** —— 在 QQ 上一边聊一边派活，不用回电脑前

这三层的依赖关系是**倒过来的**：

```
QQ 随身（入口）
      ↑ 需要
记忆连续（核心）—— 没有记忆，换到 QQ 就失忆，工作接不上
      ↑ 需要
零件可拼（骨架）—— 记忆本身、检索、注入、工具，都是一块块零件
```

所以不是“记忆 + 零件两个插件”，而是**一个工作台，记忆是它的心脏，零件是它的骨骼**。

## 2. 总体架构

```
┌──────────────────────────── dsh-workbench（一个大插件）────────────────────────────┐
│                                                                                    │
│  ┌──────────── 记忆线（memory）────────────┐   ┌──────────── 零件线（parts）────────┐ │
│  │ 六层存储 L0–L5                          │   │ 零件注册表（registry）             │ │
│  │ 写入链：扫描→信任→分级→去重→闸门        │   │ 零件契约 name/version/in/out       │ │
│  │ 检索：FTS5 + 中文 bigram                │   │ 装配引擎 compose（去重/限长）      │ │
│  │ 认知：情绪/重要性/联想                  │   │ 零件架 UI（浏览/试装/启用）        │ │
│  │ 协作：交接/派单/回执                    │   │ 零件来源：记忆包/提示词/工具/预设  │ │
│  │ 审计：哈希链                             │   └────────────────────────────────────┘ │
│  └─────────────────────────────────────────┘                    │                    │
│              │                                                  │                    │
│              └──────────────┬───────────────────────────────────┘                    │
│                             ▼                                                        │
│                    工作台服务（workbench）                                            │
│         .memory.recall/remember/compose …  .parts.list/compose …                    │
└────────────────────────────────────────────────────────────────────────────────────┘
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
   本地对话（DSH）        QQ 机器人（官方插件）      HTTP API（47810）
```

**关键点**：QQ 走的是官方 `@tencent-connect/dsh-qqbot` → `ctx.agents` → agent。
agent 调的是**同一个工作台服务**，所以 QQ 里看到的记忆和本地是**同一份**。

## 3. 两条线各自负责什么

### 3.1 记忆线（memory）—— 心脏

| 能力 | 现状 | 一期调整 |
|---|---|---|
| 六层存储 | 已有，schema v7 | 不动数据，只挪目录 |
| 写入链 / 闸门 | 已有 | 不动 |
| 检索 / 联想 | 已有 | 不动 |
| 认知（情绪/重要性） | 已有 | 不动 |
| 交接 / 派单 | 已有 | 补「未完成任务续跑」入口 |
| 面板 | 设置 / 顶栏 / 侧栏 | 合并进统一面板的第一个 tab |
| 服务 | `memory` | 挂到 `workbench.memory`，保留 `memory` 别名 |

### 3.2 零件线（parts）—— 骨骼

| 能力 | 一期做到什么 |
|---|---|
| 零件注册表 | 有：`name / version / describe / run`，落库可查询 |
| 装配引擎 | 有：`compose({ scene, parts, budget })`，去重/限长/来源标注 |
| 零件来源 | 第一阶段只接**记忆零件**（profile/recent/lessons/scene/associations），但契约是通用的 |
| 零件架 UI | 一期先出「列表 + 试装预览」，启用/编排放二期 |
| 可替换 | 二期把存储/检索/情绪也做成零件（SQLite→图库、FTS→向量） |

> 一期**不追求零件生态爆发**，只把「契约 + 注册表 + 装配」立住，
> 保证以后加任何能力都是“加一个零件”，而不是“改一次核心”。

## 4. 一个插件，怎么分两条线（目录与包结构）

### 4.1 包结构（迁移后）

```
dsh-workbench/                     ← 新的包名（对外一个安装入口）
├─ package.json                    ← name=dsh-workbench，dsh.bundle.patch 指向 cordis.patch.yml
├─ cordis.patch.yml                ← 只插入一行：id=workbench
├─ lib/
│  ├─ index.js                     ← 组装：开库 → 注册两条线 → 注册服务 → 注册 UI/路由
│  ├─ memory/                      ← 记忆线（现有代码平移，不重写）
│  │  ├─ store.js / schema.js / inject.js / tools.js
│  │  ├─ policy.js / scanners.js / emotion.js / parts.js（迁到 parts 线）
│  │  └─ …
│  ├─ parts/                       ← 零件线
│  │  ├─ registry.js               ← 零件注册与查询（落库）
│  │  ├─ compose.js                ← 装配引擎（从 lib/parts.js 演化）
│  │  └─ builtin/                  ← 内置零件：memory.profile / memory.lessons …
│  ├─ service.js                   ← workbench 服务（.memory / .parts）
│  ├─ api.js                       ← HTTP API（/memory-core/api/* 保留兼容）
│  ├─ client.js                    ← 统一面板（两个 tab：记忆 / 零件架）
│  └─ qq-official.js / qq.js       ← 保留（自建桥，默认关闭）
└─ docs/                           ← 方案 + 每期日志
```

### 4.2 兼容策略（重要）

- **包名变更但工具名不变**：`mem_*` 全部保留，26 个工具一个不改
- **数据目录不变**：还是 `D:\001\CH002\dsh-memory-data`
- **旧配置可继续用**：`dataDir/authority/api/qq*` 原样生效
- **服务名过渡**：新服务叫 `workbench`，同时仍 `provide('memory')`，旧消费者不炸
- **回退**：改回 `dsh-memory-core` 行即可，数据不动

## 5. QQ 链路（最关键的场景）

### 5.1 现状

腾讯官方插件已装好、已连通，链路是：

```
QQ → @tencent-connect/dsh-qqbot → ctx.agents → agent loop → 工具
```

### 5.2 一期要补的三件事

1. **保证 QQ agent 能看到记忆工具**
   - 验证默认 preset 是否包含 `mem_*`
   - 若不包含：提供一个 `workbench` agent preset（记忆 + 派单 + 常用工具），在 QQ 插件配置里指定

2. **「未完成工作」要能被 QQ 接上**
   - 现有 `tasks` 表 + `mem_task` 能查派单
   - 补一个 `mem_resume({ scene? })`：列出未完成任务 + 对应交接 + 相关记忆，一句话接上
   - QQ 里说「接着上次的干」→ agent 调 `mem_resume` → 直接续跑

3. **结果回传**
   - 现有 `mem_dispatch/mem_receipt` 已有状态机
   - QQ 侧补：任务完成/卡住时，用 QQ 主动发消息（官方插件支持，需确认发送通道）

### 5.3 验收场景（一期）

> 在 QQ 上：「记一下，明天把记忆底座发布流程整理成文档」
> → 关掉 QQ，回到电脑：任务在列表里、记忆里有这条
> → 第二天在 QQ 上：「接着昨天的做」
> → agent 调 `mem_resume`，列出任务与上下文，开始干

- QQ 主动消息（任务完成/卡住通知）

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 目录重组导致加载失败（BOM/路径教训） | 分步迁移：先复制后切换；每步跑回归；配置改动一律 Node 写、校验 JSON |
| 包名变更让旧 profile 找不到 | 保留 `dsh-memory-core` 兼容行一段时间（两个都能加载则报重复，需只留一个，用开关） |
| QQ agent 看不到工具 | 一期先验证；不行就提供专用 preset |
| 大插件变慢 | 两条线懒加载：零件线不影响注入链；服务按需初始化 |
| 数据风险 | 迁移前 VACUUM INTO 备份；数据目录不动 |
