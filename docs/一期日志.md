## 3. 关键实现

**3.1 注入怎么接的**

`dsh-system-prompt` 的 `context()` 接受 `text: string | (ctx) => string`，每次组装系统提示词时求值。所以：

```js
ctx.systemPrompt.context({
  name: 'memory-core',
  order: 60,
  text: () => injector.text(),   // 每次组装现算，无内容返回 ''
})
```

用 `context` 而不是 `section`：它是"模型可见的数据快照"，不是指令，更容易在压缩时整段剥离（`FENCE_RE`）。

**3.2 顺手修掉的隐藏 bug**

旧 `inject.js` 的查询写了 `WHERE valid_to IS NULL`，但 v3/v4 表结构里**没有这一列**。查询必抛错，被 `catch` 吞掉后返回空串——也就是说，即使接上，注入也永远是空的。本期去掉该条件。

**3.3 闸门公理**

```js
if (!tainted && trustLevel !== 'trusted' && sourceChannel !== 'user' && origin !== 'legacy_import') {
  status = 'pending'; pendingReview = 1; reviewReason = 'unverified-source'
}
```

`review(approve | release)` 时把 `trust_level` 升为 `trusted`——**闸门裁决即确认**。

**3.4 组合检查**

```js
const key = row.batch_id || row.source_channel || row.record_id
if (used.get(key) >= maxPerGroup) continue   // 默认每组 1 条
```

同一次会话/同一来源的多条记忆，不会同时进入注入块。

## 5. 注意事项（重要）

1. **需要重启宿主**才生效。ESM 模块按 URL 缓存，改文件不会热更新；当前进程仍在跑旧代码。
2. **真实库会在下次打开时迁移到 v4**。迁移只发生一次，是幂等的。
3. **归档库不要再用新代码打开**：昇腾那份也是"v4"，但它是另一套 v4（有 `valid_from/valid_to`、没有 `batch_id`），版本号相同会被误判为已迁移。
4. **两个进程共用同一库**：desktop 与 web 同时读写靠 WAL，写操作有 `busy_timeout`。迁移只应由先启动的那个进程完成。
5. **注入是快照，不是按 query**：目前每轮固定带 top-3 指针；查询相关的召回仍靠模型调 `mem_search`。若要按 query 注入，需要接 `agent/pre-step`（可作为二期可选项）。
6. **闸门会改变行为**：以后来自网页/IM 的写入会先进待审，不会立刻出现在召回里。
